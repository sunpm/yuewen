## 上线方案

<a id="deployment-steps"></a>

### 默认部署路径

1. 一个 Netlify 项目构建并发布 Vue 静态前端和 Node.js Functions，通过同源 `/api/*` 访问 Hono；生产方案不再需要 Docker 主机或自建反向代理。
2. 日常本地开发沿用 `pnpm dev`；部署前使用 Netlify Dev / Deploy Preview 核验实际函数入口。构建配置沿用现有前端产物、函数目录、API 重写与 SPA 回退顺序，具体入口约束见[开发说明](../development.md)，不因旧架构草案重新建立常驻服务或第二套路由；预览部署与生产使用隔离的数据库及环境配置。
3. 先接入 PostgreSQL、Key 加密配置和应用域名以联调游客链路，再接邮箱与认证配置以联调账号保存连接；邮箱未配置或不可用不应阻断游客使用。敏感配置仅供函数使用，不写入前端 `VITE_*` 变量或公开构建产物。
4. 在 Netlify 绑定 `read.sunpm.me`，在 Cloudflare 的 `sunpm.me` 区域添加 `read` 的 CNAME，指向 Netlify 实际分配的站点地址；完成 HTTPS 与登录 Cookie 验证。仅配置本站子域名，保留根域现有用途。参考[外部 DNS 配置](https://docs.netlify.com/manage/domains/configure-domains/configure-external-dns/)。
5. 在 Resend 添加 `mail.read.sunpm.me`，通过 Cloudflare 配置控制台实际给出的验证记录，完成[发信域名验证](https://resend.com/docs/dashboard/domains/introduction)。使用[域名、云资源与邮件命名](#naming)确定的发件人发送登录与密码重置邮件，核实投递和限流。
6. 分别验收游客接入、登录保存连接、已有账号 Key 冲突、失效重配、分批采集、刷新续传、函数冷启动、临时凭证与报告过期清理、下载和退出，记录实际函数耗时及额度消耗；以 Deploy Preview 检查修改，通过后再发布生产版本。
7. 准备 Netlify 部署回滚、兼容的数据库迁移、数据库备份恢复及独立的加密密钥保管方式。删除账号或 Key 后，在线数据立即失效，备份副本按明确保留期限清理，恢复时不得重新启用已删除的凭证。

生产方案采用分批请求与共享临时缓存，不依赖请求结束后的进程存活，也不把登录、任务状态或限流计数仅存在某个实例内存中。数据库暂时不可用时提示服务故障，不将其显示为 Key 失效。具体数据库连接方式和函数区域在实施时验证，避免连接数随函数并发失控，并检查到微信读书网关的实际连通性。

用户已提供根域 `sunpm.me`，并授权确定本站子域名、Neon 和邮件命名；具体方案见[域名、云资源与邮件命名](#naming)。用户已确认验证码发信邮箱配置在环境变量中，后续联调核对现有服务配置，仅补实际缺项。本文件记录部署目标；资源创建、DNS 修改、配置是否已同步各部署环境及发布是否完成，以实际操作记录和验收证据为准。

### 域名、云资源与邮件命名

用户已授权代为确定命名，本项目采用以下方案。产品面向用户始终显示「阅纹」，云平台资源统一使用易识别的 `sunpm-read`。

| 项目                | 确定名称 / 地址                                   | 用途                                            |
| ------------------- | ------------------------------------------------- | ----------------------------------------------- |
| 正式网站            | `https://read.sunpm.me`                           | 阅纹唯一正式入口；`read` 简短，直接表达阅读用途 |
| API 地址            | `https://read.sunpm.me/api`                       | 前后端同源，首版不另设 API 子域名               |
| Netlify 项目名      | `sunpm-read`                                      | 前端与 Functions 同项目部署                     |
| Neon 项目名         | `sunpm-read`                                      | 阅纹的 PostgreSQL 项目                          |
| PostgreSQL 数据库名 | `yuewen`                                          | 两个环境保持同名，通过各自分支连接串区分        |
| Neon 生产分支       | `production`                                      | 仅供正式部署使用                                |
| Neon 开发分支       | `development`                                     | 本地开发与首版单个活动预览使用，数据与生产隔离  |
| 邮件服务            | Resend                                            | 登录验证码和密码重置邮件                        |
| Resend 验证域名     | `mail.read.sunpm.me`                              | 阅纹专用发信子域名                              |
| 发件人显示名        | `阅纹`                                            | 用户收件箱中看到的名称                          |
| 发件人地址          | 读取对应环境的 `EMAIL_FROM`，用户已确认已配置     | 验证码及密码重置专用；与意见反馈收件邮箱不同    |
| Resend API Key 标签 | `sunpm-read-production`、`sunpm-read-development` | 区分生产与开发用 Key；此处仅为标签，不是凭据值  |
| 邮件标题            | `【阅纹】登录验证码`、`【阅纹】重置密码`          | 区分两种事务邮件用途                            |

网站解析使用 Netlify 实际分配的 CNAME 目标；若 `sunpm-read` 平台站点名被占用，可保留平台生成的内部名称，正式域名仍为 `read.sunpm.me`。命名是目标约定，资源是否已创建以及当前配置是否生效，应在实际部署时核对控制台与验收记录；不依据旧计划断言平台仍未创建资源。

Neon 的两个分支使用独立连接串。公开预览使用模拟示例或脱敏数据；本地开发按[开发来源说明](../development.md#development-source)使用本地联调 Key 读取真实报告，临时保留在内存，不复制生产数据库。开发库优先通过仅复制结构的分支或空库迁移初始化，不把已有生产账号、Key 和报告复制到开发环境。首版不自动为每次预览创建新分支；并行预览有实际需要时再调整。参考 [Neon 分支工作流](https://neon.com/docs/get-started-with-neon/workflow-primer)。

邮件使用独立子域名，便于区分阅纹的账号邮件，并管理发信信誉；这也符合 [Resend 的子域名建议](https://resend.com/docs/knowledge-base/is-it-better-to-send-emails-from-a-subdomain-or-the-root-domain)。Cloudflare 中的 DKIM、SPF、Return-Path 等记录名称和值以 Resend 控制台实际结果为准，不在计划中猜测；网站 CNAME 与邮件验证记录分别配置。

验证码与密码重置邮件使用对应环境已有的 `EMAIL_FROM`，通过 Resend 发信；用户于 2026-10-04 确认该邮箱已配置，不再要求重复提供或替换。本轮仅记录用户提供的配置状态，未读取环境变量值，也未验证真实投递或部署环境同步。意见反馈使用[设计计划中的独立收件邮箱](design.md#theme-and-feedback)，不用于验证码发信。两类邮箱用途分开，首版事务邮件不设置 `Reply-To`，正文说明其为自动通知，不因反馈邮箱已存在而自动配置回复地址。验证码邮件不启用打开和点击追踪。正式环境的认证基址为 `https://read.sunpm.me`，邮件内站点链接也使用该地址；预览和本地环境使用各自的应用地址，不共用生产会话或凭据。

<a id="gates"></a>

### 不可用平均分抵消的硬门槛

- 游客主流程与按需登录分支完整，未连接、游客会话到期、未配置/失效 Key、登录过期、保存冲突、空数据、上游失败、取消和退出都有明确且可操作的状态；查看和下载不以登录为前提。
- 无用户之间串数据、凭证进入日志/URL/导出、笔记原文注入页面等问题。
- 无错误单位、混淆统计范围、把未知填零、编造划线或假装完整采集的问题。
- 各目标尺寸无页面级意外横向溢出、文字意外裁切、图表标签遮挡、关键控件不可见或无法操作的问题。书架卡片明确设计的两行省略允许保留，详情必须可读完整标题；日历和横向书架等明确设计为横向浏览的区域可在自身容器内滚动并提供提示，不能撑宽整个页面。缩放和键盘操作下同样核验这些边界。
- 示例、真实报告与下载产物标识准确；离线 HTML 断网后仍能读到正文、图表和范围说明。
- 主要浏览器中无阻断流程的控制台错误或持续失败请求。

<a id="review"></a>

### 每轮检查方法

1. 固定数据版本、浏览器、视口与主题，截图覆盖首页、概览、深度报告、书架、笔记、详情和异常状态。
2. 对照本计划和参考体验逐项标注具体问题：位置、影响、优先级、调整方式。严重问题先修。
3. 修改后重看同一场景，并检查受改动影响的相邻页面；保留前后对比和操作结论。
4. 至少完成排版构图、交互状态、真实数据密度三个方向的检查；未过门槛就继续修订，不以固定轮数结束。
5. 最后一轮检查完整主流程、线上构建和导出文件。记录未能验证的项目，不把它们算作通过。

在 [quality-log.md](../quality-log.md) 记录每轮日期、版本、场景、截图位置、问题、修复、复核与评分依据。现有页面和部分检查已完成，完整品质验收尚未完成；历史通过记录不能代替后续改动的验收。

<a id="validation"></a>

### 性能与验证边界

以[Core Web Vitals](https://web.dev/articles/vitals)的良好体验阈值为线上目标：LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1。真实用户数据积累前，不用本地一次测量冒充线上 p75 达标。

开发阶段在固定条件下检查示例与报告页；公开首页的 Lighthouse 目标为 Performance ≥ 90、Accessibility ≥ 95、Best Practices ≥ 95、SEO ≥ 90。记录环境与分数，报告页另检查图表加载、长列表滚动和筛选响应。上游采集时间单独统计，不把它混入纯页面渲染性能；先取得基线再定真实报告耗时目标。

现有工程已经使用 Vitest、Vue Test Utils、Playwright。沿用当前全局规则，除非用户明确要求，不新增或修改自动化测试；实施时运行适用的已有测试、类型检查、lint、双端构建和浏览器实际操作。最新通过、失败及未验证项统一记录在 [quality-log.md](../quality-log.md)。

已有检查失败时区分产品缺陷、测试与已确认新需求的失配、运行环境故障。产品缺陷修复后复核；失配或环境故障保留原始失败结果，使用允许的现有检查和人工操作另记行为证据，不修改测试来追平结果，也不把人工通过改写成自动化通过。尚无充分证据的功能、隔离或兼容性硬门槛继续待验收，不能以记录了限制代替通过。
