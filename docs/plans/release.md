## 上线方案

<a id="deployment-steps"></a>

### 默认部署路径

1. 默认一个 Netlify 项目构建并发布 React PC（目标）、冻结 Vant H5、独立 React 后台和 Node.js Functions，通过同源 `/api/*` 访问 Hono；后台新增规则见[后台部署](#console-deployment)，不需要 Docker 主机或自建反向代理。
2. 日常本地开发沿用 `pnpm dev`；部署前使用 Netlify Dev / Deploy Preview 核验实际函数入口。构建配置沿用现有前端产物、函数目录、API 重写与 SPA 回退顺序，具体入口约束见[开发说明](../development.md)，不因旧架构草案重新建立常驻服务或第二套路由；公开预览不连接数据库或 R2，不配置生产凭据；本地和受控测试部署使用隔离开发配置。
3. 先接入 PostgreSQL、Key 加密配置和应用域名以联调游客链路，再接邮箱与认证配置以联调账号保存连接；邮箱未配置或不可用不应阻断游客使用。敏感配置仅供函数使用，不写入前端 `VITE_*` 变量或公开构建产物。
4. 在 Netlify 绑定 `read.sunpm.me`，在 Cloudflare 的 `sunpm.me` 区域添加 `read` 的 CNAME，指向 Netlify 实际分配的站点地址；完成 HTTPS 与登录 Cookie 验证。仅配置本站子域名，保留根域现有用途。参考[外部 DNS 配置](https://docs.netlify.com/manage/domains/configure-domains/configure-external-dns/)。
5. 在 Resend 添加 `mail.read.sunpm.me`，通过 Cloudflare 配置控制台实际给出的验证记录，完成[发信域名验证](https://resend.com/docs/dashboard/domains/introduction)。使用[域名、云资源与邮件命名](#naming)确定的发件人发送登录与密码重置邮件，核实投递和限流。
6. 公开 Deploy Preview 只验模拟页面、静态路由与构建隔离，不在其上执行真实登录、游客或管理写入。真实流程先在本地/Netlify Dev 的隔离开发库验证，再对正式环境执行已获授权的有界验收；如确需远端联调，另建明确受控的测试部署与隔离配置，不放开普通 PR 预览。覆盖游客接入、登录保存、冲突、失效重配、分批采集、恢复、清理、下载和退出，记录函数耗时与额度。生产个人 Key 的使用继续遵守现有用途授权，见质量记录。
7. 准备 Netlify 部署回滚、兼容的数据库迁移、数据库备份恢复及独立的加密密钥保管方式。删除账号或 Key 后，在线数据立即失效，备份副本按明确保留期限清理。启用新增持久数据前确定实际备份期限、恢复窗口及删除记录在恢复点之外的保存方式；先在隔离库恢复，补执行恢复点后的删除/撤销并使旧会话与临时报告失效，再开放服务。R2 缺失图片按已删除处理；不能重放删除记录时保持恢复环境隔离，不能只恢复旧数据库就重新开放账号或附件。

生产方案采用分批请求与共享临时缓存，不依赖请求结束后的进程存活，也不把登录、任务状态或限流计数仅存在某个实例内存中。数据库暂时不可用时提示服务故障，不将其显示为 Key 失效。具体数据库连接方式和函数区域在实施时验证，避免连接数随函数并发失控，并检查到微信读书网关的实际连通性。

用户已提供根域 `sunpm.me`，并授权确定本站子域名、Neon 和邮件命名；具体方案见[域名、云资源与邮件命名](#naming)。用户已确认验证码发信邮箱配置在环境变量中，后续联调核对现有服务配置，仅补实际缺项。本文件记录部署目标；资源创建、DNS 修改、配置是否已同步各部署环境及发布是否完成，以实际操作记录和验收证据为准。

<a id="batch-release"></a>

### 分批发布与启用门槛

主分支合并会触发生产发布。PC4 已按用户确认的关键流程验收切换 React PC，根构建仅产出 PC、冻结 H5 和后台。默认不再要求多浏览器、全尺寸及完整辅助技术矩阵；未执行的专项保留质量记录，不写成通过。独立后端改动仍须兼容当前 PC 和冻结 H5。数据库先做向前兼容迁移，再发布消费新结构的代码；回滚保留新增表与对象删除任务，不用反向删表代替回滚。启用反馈后，回滚版本也必须继续处理附件删除和到期清理。

每个发布批次执行 C5 中适用的检查：PC 批次检查 PC 与受影响共享/H5 能力；后台批次增加管理鉴权和 `/console`；反馈批次增加 R2、账号自助删除、清理与审计；统计单独验证文档隔离。尚未交付的接口和入口保持关闭，不能只隐藏菜单；C0–C1 可合并独立后台静态入口与默认未配置的认证代码，管理 API 在缺少独立密钥时返回 503 且不访问新表，生产迁移和管理身份启用留待对应验收完成；未来功能不作为当前批次的完成前提，已有功能、数据和权限硬门槛也不能因分批而省略。全部启用后再记录 P6 完成，原 P4/P5 缺项继续保留。

2026-10-12 C4 基础统计代码完成，用户确认本批免浏览器验收、生产开通留到 C5。当前不开通 Cloudflare 站点、不设置生产 token。C5 按[实际统计配置](../development.md#pc-analytics)核对手动接入和无自动注入，再配置 Production 开关与站点 token、部署并记录公开页 PV/性能及私有文档隔离证据；可选业务转化不包含在这次开通中。

纯计划或文档提交可沿用 `[skip netlify]` 避免无业务变化的部署；它只影响部署，不替代文档格式与差异检查，也不用于跳过代码改动的构建或验收。

网站解析使用 Netlify 实际分配的 CNAME 目标；若 `sunpm-read` 平台站点名被占用，可保留平台生成的内部名称，正式域名仍为 `read.sunpm.me`。命名是目标约定，资源是否已创建以及当前配置是否生效，应在实际部署时核对控制台与验收记录；不依据旧计划断言平台仍未创建资源。

验证码与密码重置邮件使用对应环境已有的 `EMAIL_FROM`，通过 Resend 发信；开发环境真实验证码投递和登录已有一次验证，生产完整流程与配置同步仍按质量记录核验，不要求重复提供已配置邮箱。截图反馈改用本站接口，[独立反馈邮箱](design.md#theme-and-feedback)只作故障联系，不用于验证码发信。事务邮件不设置 `Reply-To`，正文说明其为自动通知，也不启用打开和点击追踪。正式环境的认证基址为 `https://read.sunpm.me`，邮件内站点链接也使用该地址；本地与受控测试使用各自应用地址，公开预览不使用生产会话或凭据。

### 后台子路径与备用域名

首选 `https://read.sunpm.me/console`，后台产物为 `dist/console/`，Vite `base` 为 `/console/`，React Router 基址为 `/console`；前台 `/` 和 `/m/` 保留。Netlify 已支持 [SPA 重写](https://docs.netlify.com/manage/routing/redirects/rewrites-proxies/)，2026-10-09 已接入 `/console` 和 `/console/*` 重写，并通过包含后台的四入口构建；浏览器与平台管理登录验收仍待完成。

重写优先级为 `/api/*` → `/console` 精确入口与 `/console/*` → `/m/*` → 桌面 `/*`；后台回退到 `/console/index.html`，静态资源优先，不能强制把 JS/CSS 重写成 HTML。验证带/不带尾斜杠、`/console/login`、`/console/users`、刷新、登录返回和未知后台路由；当前不新增设备自动分流，统计排除管理页面和冻结 H5。构建顺序避免桌面清空其他两端产物，部署检查确认三个入口同时存在。

后台 API 使用 `https://read.sunpm.me/api/console`，管理 Cookie、来源校验、独立认证及初始化见[超管计划](console.md#admin-auth)。本地 `.env` 只提供预设，不会自动同步 Netlify 或创建生产超管；生产独立配置 `CONSOLE_AUTH_SECRET` 和随机初始化凭据，值不入仓库，不以缺少 Resend 判定管理密码登录不可用。后台配置、截图存储迁移和账号删除/附件清理完成后才允许启用反馈主入口；公开预览继续只有模拟能力，不开放真实管理账户或附件。

只有实际平台/路径验证不能解决时，启用用户指定的备用地址 `https://console-read.sunpm.me`，独立 Netlify 站点名建议 `sunpm-read-console`。备用站点只部署后台静态产物与同一后端代码的管理入口，后台 API 同源提供；管理 Cookie 使用 host-only，不设置 `.sunpm.me` 域 Cookie，不开放宽泛 CORS，也不复制一套业务数据库或重复运行清理任务。该路径需要单独验证 DNS、TLS、认证来源、迁移和发布回滚；本轮不创建站点、不修改 DNS。

新增发布门槛：管理越权拒绝、反馈附件归属/容量/删除、数据库迁移、三入口深链接、PC 迁移与冻结 H5 兼容、第三方统计不进入私有页面。各项按[后台测试清单](console.md#tests)验收；不能凭前台构建通过认定后台可发布。统计的可选转化不阻塞反馈后台交付。

<a id="r2-deployment"></a>

### R2 配置与验收

截图使用私有 Standard bucket，生产命名 `sunpm-read-feedback-production`，开发命名 `sunpm-read-feedback-development`；开发 bucket 已于 2026-10-13 创建，生产仍为计划值。两环境使用独立 bucket 和限制到对应 bucket 的最小读写凭据，公开预览不配置 R2 写权限。不启用公共 `r2.dev` 地址，不将附件作为静态网站资源发布。

已提供服务端配置项；启用时在本地忽略配置与 Netlify Functions 配置 `R2_ACCOUNT_ID`、`R2_ACCESS_KEY_ID`、`R2_SECRET_ACCESS_KEY`、`R2_BUCKET`；S3 endpoint 根据账号构造，不注入 `VITE_*`。`.env.example` 只写变量名/空占位，凭据留在私有环境。R2 接入不要求另建 Worker，不改变现有网站 DNS 或后台地址。C2 后端批次默认 `FEEDBACK_ENABLED=false`；先迁移、配置私有 bucket 与 30 天生命周期并完成对应验收，再显式开启。关闭反馈开关不会停掉已迁移数据的清理与账号删除适配。

开发 bucket 已配置 30 天对象生命周期并保持公共开发 URL 与自定义域关闭，关键 API 结果见[开发 R2 记录](../quality-log.md#c2-development-r2-2026-10-13)。生产启用时配置相同生命周期；应用自行即时拒绝过期读取，并持续重试删除任务和回收未完成上传。上线验私有对象不可匿名读取、开发/生产隔离、真实上传与读取、R2 故障、数据库最终写入失败、上传中删除账号、到期清理、孤儿回收及恢复后缺图。服务端内存/请求体和管理读取流量单独测量，不把“图片存 R2”解释为函数零资源消耗。

## 品质自查与反复改进

<a id="quality-goals"></a>

### 参照方式

[Awwwards 作品评分页](https://www.awwwards.com/sites/self-aware)提供设计、可用性、创意、内容等评估视角；[Webby 官方标准](https://www.webbyawards.com/judging-criteria/)进一步强调内容、导航、功能、交互、创新与整体体验。FWA 作为原创数字体验的对标目标；本计划不声称掌握或复刻其官方评分公式。

内部采用以下专用检查表。这是本项目的验收方法，分数不等同于任何奖项分数。

| 维度           | 权重 | 要检查的实际结果                                                                        |
| -------------- | ---- | --------------------------------------------------------------------------------------- |
| 视觉与排版     | 25   | AIHOT 布局适配、冗余信息精简、中文层级、留白、密度、封面与图表一致性；PC 页面与主题完成 |
| 使用与导航     | 20   | 新用户能理解接入方式，示例可探索，筛选/详情/下载/退出明确且可恢复                       |
| 数据与叙事     | 20   | 单位和范围正确，结论有来源，缺失与零值分开，长短报告均易读                              |
| 原创交互       | 15   | 阅读轨迹、证据展开和笔记回顾形成与内容相关的独特体验                                    |
| 工程与性能     | 10   | 首屏、图表、长列表和采集过程稳定，构建通过，线上可运行与回滚                            |
| 可访问性与适配 | 10   | 键盘、焦点、对比度、减少动效、缩放和不同屏幕下核心功能完整                              |

当前品质评估面向 PC 与后台。H5 完整视觉、物理手机与功能优化专项暂停，旧失败和未验证项保留；构建或共享接口受影响时仍做既有能力兼容检查。

以上评分用于用户明确要求的完整品质专项，不自动成为每次需求或发布前置。所有需求默认执行 [AGENTS.md 的最小必要验收](../../AGENTS.md#验收范围与效率)：受影响的已有检查与一次 Chrome 关键流程，通过后立即收尾。专项评分仍须有证据，不能只填写“完成”。

<a id="gates"></a>

### 不可用平均分抵消的硬门槛

- 游客主流程与按需登录分支完整，未连接、游客会话到期、未配置/失效 Key、登录过期、保存冲突、空数据、上游失败、取消和退出都有明确且可操作的状态；查看和下载不以登录为前提。
- 无用户之间串数据、凭证进入日志/URL/导出、笔记原文注入页面等问题。
- 无错误单位、混淆统计范围、把未知填零、编造划线或假装完整采集的问题。
- 各目标尺寸无页面级意外横向溢出、文字意外裁切、图表标签遮挡、关键控件不可见或无法操作的问题。书架卡片明确设计的两行省略允许保留，详情必须可读完整标题；日历和横向书架等明确设计为横向浏览的区域可在自身容器内滚动并提供提示，不能撑宽整个页面。缩放和键盘操作下同样核验这些边界。
- 示例、真实报告与下载产物标识准确；离线 HTML 断网后仍能读到正文、图表和范围说明。
- 主要浏览器中无阻断流程的控制台错误或持续失败请求。

<a id="review"></a>

### 每轮检查方法

1. 固定数据版本、浏览器、视口与主题，截图覆盖首页、概览、深度报告、书架、笔记、详情和异常状态。
2. 对照本计划和参考体验逐项标注具体问题：位置、影响、优先级、调整方式。严重问题先修。
3. 修改后重看同一场景，并检查受改动影响的相邻页面；保留前后对比和操作结论。
4. 至少完成排版构图、交互状态、真实数据密度三个方向的检查；未过门槛就继续修订，不以固定轮数结束。
5. 最后一轮检查完整主流程、线上构建和导出文件。记录未能验证的项目，不把它们算作通过。

在 [quality-log.md](../quality-log.md) 记录每轮日期、版本、场景、截图位置、问题、修复、复核与评分依据。现有页面和部分检查已完成，完整上线品质专项尚未完成；稳定历史流程沿用已有证据，仅复核本次改动与直接影响。

<a id="validation"></a>

### 性能与验证边界

以[Core Web Vitals](https://web.dev/articles/vitals)的良好体验阈值为线上目标：LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1。真实用户数据积累前，不用本地一次测量冒充线上 p75 达标。

开发阶段在固定条件下检查示例与报告页；公开首页的 Lighthouse 目标为 Performance ≥ 90、Accessibility ≥ 95、Best Practices ≥ 95、SEO ≥ 90。记录环境与分数，报告页另检查图表加载、长列表滚动和筛选响应。上游采集时间单独统计，不把它混入纯页面渲染性能；先取得基线再定真实报告耗时目标。

React PC 与 console 的构建同时核对[入口依赖、样式与按需加载](pc-refresh.md#engineering)，记录各入口 JS/CSS 和懒加载模块体积、固定数据下的交互基线；不只以构建成功判断隔离。检查缓存期限与身份变化清理、聚焦/重连恢复、离线操作不自动补交，以及图表渲染或路由模块加载失败后的恢复。PC2 完整链路先验收，再按 PC1 的旧路由/业务状态对应表扩展页面；实际证据与未通过项继续写入质量记录。

现有工程已经使用 Vitest、Vue Test Utils、Playwright。2026-10-04 用户在新增后台需求中明确要求测试：后台、截图反馈、用户/表管理、统计及直接受影响的回归，允许并要求新增或修改必要自动化测试，具体见[后台测试计划](console.md#tests)；React 组件补 Testing Library，现有工具按需扩展。设备自动入口的实施与测试随 H5 重构推迟。此次 PC 迁移与精简只新增计划，不产生新的测试代码授权；运行既有检查，需求失配如实记录，以人工操作补充验证。此前授权不扩展到无关旧功能，其他工作继续遵循未明确要求则不新增或修改测试的全局规则。按阶段运行适用测试、类型检查、lint、构建和浏览器实际操作；后台接入后根检查覆盖三个入口。结果统一记录在 [quality-log.md](../quality-log.md)。

已有检查失败时区分产品缺陷、测试与已确认新需求的失配、运行环境故障。产品缺陷修复后复核；本次授权范围内的需求失配可以按新行为更新测试，必须保留有意义的断言及原失败记录，不为了通过而删用例、跳过或弱化断言。范围外失配和环境故障继续记录，并使用允许的检查与人工操作补证据；人工通过不能改写成自动化通过。尚无充分证据的功能、隔离或兼容性硬门槛继续待验收。
